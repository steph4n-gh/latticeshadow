# Packaged macOS app: consent wording candidate

This report covers the **exact** unsigned Apple Silicon app built from source
commit `20669ff7e65fd3045e8c8f3151bdda5b07013047`. Its ZIP is
425,565,640 bytes, SHA-256
`6f5e00f2ca44ab85956b47169adb2dd29475e81450ca3db2951f2c319e1a09d6`.
The checksum matched in the build guest, transfer directory, and stripped
install guests. This is an internal test artifact, not a public download.

`verify_app.py` passed on the build guest: version 0.2.0, arm64 launcher,
offline bundled-model and native-resource smoke, ad-hoc signature, and 307
Mach-O dependency links. The unpacked app contained 1,098,432,784 file bytes.
Its pinned model revision was `f60985c706f192d45d218078e49e5a8b6f15283a`;
the model weight SHA-256 was
`164fc63ee9f9267be7378fcbd7df99d09788a2f45244c92aa99ae5a574925716`.

## Stripped guest and destructive-action wording

Disposable guests were cloned from a macOS 26.6.2 CI base image. Homebrew and
Xcode Command Line Tools were moved out of their normal locations **before**
installing the exact ZIP under `/Applications`. All data were synthetic; host
clipboard sharing was off. The installed app's `shadow --help` described
`shred` as crypto-shredding the entire local memory vault.

With a synthetic note present, `shadow shred` warned that the operation would
destroy the **entire** local vault, including notes, terminal records, and
captured clipboard entries, and required the literal `SHRED` confirmation.
A nonconfirming answer aborted. The note remained searchable afterward.

With network model access disabled, `shadow remember note` saved a synthetic
record under an explicit project. A project-scoped offline `shadow timeline
--query --json` returned the exact ID and text. The command's stdout parsed as
JSON; its native-extension fallback notice was on stderr. The command still
worked after the aborted shred. Installing or exercising this app did not
enable a capture source.

## Fresh-target portable restore

A third stripped guest began with no default vault or key and installed the
same ZIP. It restored a retained **synthetic** portable archive exported by
the earlier `b603442` app. The archive SHA-256 was
`80f0d02edb14e92b9b20f2ecd73dce4c2468956ba5f503e5e63da8dc07ed87ed`.
The restored key had mode 0600. Two independent inspection processes reopened
the private destination; its one deletion tombstone remained. Activation into
the empty default profile produced valid JSON with both retained event IDs,
and their canonical fields matched the source fixture. The first use migrated
the restored legacy flat-file key to a Keychain keypair-wrapped key.

A deliberately wrong synthetic passphrase failed authentication, created no
destination, produced no py2app launch error, and left the successful restore
inspectable. This proves that the exact candidate can **restore** the retained
older archive. It does not establish a populated 0.1.0 wrapped-key upgrade.

## Exact-artifact export and fresh-target restore

A fourth and fifth stripped guest repeated the portable-backup journey using
the `20669ff` ZIP at **both** ends. The source guest saved three synthetic
notes, forgot one, and confirmed two retained event IDs plus one deletion
tombstone. It exported a new encrypted archive of 971 bytes, SHA-256
`5fe69a2d5e318d1932425882913cdeec687e2c8073ac82f4da2e83134919db56`.
The source guest and the separate fresh target each matched the exact app ZIP
checksum before use.

The target began with no default vault or key. It restored to a private
destination with a mode-0600 key, inspected that destination in two separate
processes, and confirmed the deletion tombstone. Activation into the empty
default profile produced valid JSON. The two retained IDs and their canonical
fields matched the source timeline. First use migrated the restored flat-file
key to a Keychain keypair-wrapped key.

A deliberately wrong synthetic passphrase then failed authentication,
created no rejected destination, and produced no py2app launch error. The
recovered vault's inspection output was unchanged, and the activated default
vault still returned the same two canonical events. This establishes a
bounded, exact-artifact export, restore, activation, and rejection check; it
does not establish restore across every supported macOS or Keychain state.

## Exact-artifact daemon and consent lifecycle

In another fresh stripped guest, `shadow install` wrote the LaunchAgent but
left the daemon **STOPPED**. A synthetic clipboard value was present before
`shadow consent set clipboard on`, `shadow consent set terminal_history off`,
and `shadow enable`. The enabled daemon was **RUNNING**, but its vault still
held zero entries after four seconds. A later synthetic copy increased the
entry count from zero to one. Host clipboard sharing was disabled.

`shadow pause` showed **RUNNING / PAUSED**. A different synthetic copy while
paused did not increase the entry count. Before a normal in-guest reboot, the
config, an adjacent canary, and the wrapped `.key` were checksummed. All three
checksums matched after reboot, and `shadow status` reported **RUNNING /
PAUSED** with one vault entry. `shadow disable` stopped the daemon. `shadow
remove`, with its default No answer to deleting data, removed the LaunchAgent
while preserving the `.key` checksum and the one vault row.

These checks cover one normal reboot in this CI-base guest. They do not
establish behavior after an abrupt VM stop or on a stock first-launch Mac.

## Limits

The earlier `b603442` artifact has separate GUI, performance, and recovery
evidence. Those results do not become exact-`20669ff` results by implication.
This report does not cover the exact candidate's interactive GUI journey; its
[logged-in menu/Recall smoke](desktop-gui.md) is recorded separately. A
populated 0.1.0 wrapped-key upgrade
remains unverified, as recorded in the separate legacy-upgrade report. The
guests began as CI images with Gatekeeper assessment disabled; this does not
establish stock Gatekeeper first launch. Developer ID signing and notarization
remain pending before any public binary release.
